### 4.1 — Seven-stage sales pipeline, built and tested end to end
*GoHighLevel · my own business*

A full sales pipeline for an Amazon PPC management business, built inside HighLevel and tested to the last email.

- Seven stages: New Lead, Contacted, Appointment Booked, Consultation Completed, Proposal Sent, Closed Won, Closed Lost
- A probability ladder at 10 / 25 / 40 / 60 / 75 / 100 / 0, where only the two terminal stages carry an honest number
- Seven workflows, one per stage, each tested end to end with every email verified in a real inbox
- Entry covered by a form trigger and a booking trigger together, because a stage-change trigger never fires for the first stage

**What it proves:** I build pipelines that survive contact with real leads, and I test the delivery rather than trusting the execution log.

### 4.2 — Rendezvous QR Setter
*Live · multi-tenant · writes into HighLevel over the API*

One printed QR code that keeps working after the event ends. A prospect scans it, fills a short form, and lands in HighLevel already tagged to the event they were standing at.

- Live at `go.workwidkirk.com`, with the original single-tenant version still serving at `qr.workwidkirk.com`
- Multi-tenant: a page per handle, each with its own HighLevel credentials, logo, photo, and colours
- Contacts created and auto-tagged `event-<slug>` through HighLevel's API v2, authenticated with a Private Integration Token
- Six scan-page templates, and 959 tests green

**What it proves:** I work HighLevel from both sides, inside the builder and against the API when the builder cannot do the job.

### 4.3 — Dental practice pipeline blueprint
*Design work · not a shipped client build*

Three mapped pipelines for a dental practice: new patient, recall, and treatment acceptance. Stage definitions, entry and exit conditions, and the workflow that has to sit behind each transition.

- Covers the awkward stages most maps skip, including waiting on a decision, follow-up needed, and declined for now
- Written as a build spec, so the pipeline can be built from the document without a second discovery call

**Framed honestly:** this is a blueprint, not a live client account.

### 4.4 — An Amazon PPC web application
*FastAPI · PostgreSQL · deployed*

A multi-user web application holding the tools I use to run Amazon ad accounts. Built because the manual version was costing hours every week.

- Bid Optimizer, Placement Optimizer, Bid Reversion, Keyword Relevancy Checker, PDP Info Grabber, and a search-term analyser, all behind one login
- FastAPI backend, PostgreSQL, JWT auth, deployed and in daily use

**What it proves:** when a build needs to leave HighLevel for a custom tool, a real database, or an integration, I can take it there.

## 6. Process

Section eyebrow: `04 / HOW IT GOES`
Heading: **Four steps. You are needed for two of them.**

**01 — Call**
Fifteen minutes on what breaks today. You leave with the shape of the build and a price, not a proposal to be sent later.

**02 — Map**
I write the pipeline, the stages, and every workflow as a document before building anything. You approve the map. Changes are cheap here and expensive later.

**03 — Build and test**
I build it in your sub-account and run real leads through it: real emails, real inboxes, real stage moves. Nothing is called done because a log said delivered.

**04 — Handoff**
A one-page document, plus notes inside the workflows themselves, so whoever inherits it can read what each step does without calling me. Keeping me on retainer afterwards is a decision, not a dependency.
